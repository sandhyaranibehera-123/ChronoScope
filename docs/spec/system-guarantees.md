# CHRONOSCOPE — System Guarantees

> **Guiding principle**: CHRONOSCOPE does not use complexity as a feature. Every distributed component exists because it demonstrates a specific consistency, reliability, causality, execution, or recovery property that can be measured and verified.

This document is the frozen architecture specification for CHRONOSCOPE, produced through seven rounds of design review before implementation began. It is the canonical reference during implementation: **do not "improve" the architecture while implementing it.** When something appears inconvenient, check the relevant invariant, the transaction boundary, the data-ownership rule, and the package boundary before changing the implementation — and if a genuinely necessary architectural change is found, document it as an ADR (see `docs/adr/`), never a silent edit.

## Persistence split: MySQL + MongoDB

CHRONOSCOPE is a deterministic distributed-systems laboratory (event sourcing, CQRS, replay, timeline branching, causal graphs, chaos engineering, recovery verification, performance benchmarking) — a portfolio-grade demonstration project, deliberately excluding Kubernetes (see `docs/adr/014-why-not-kubernetes.md`).

- **MySQL is the write side / source of truth** — `chronoscope_core` (events, `aggregate_versions`, `aggregate_state`, timelines, outbox, snapshot metadata, users) and `chronoscope_ops` (jobs, experiments, audit, control commands, projection inbox/checkpoints). Everything here depends on strict ACID transactions, row-level locking, `FOR UPDATE`/OCC, and foreign-key referential integrity. **The event store itself does not move to MongoDB** — moving it would discard the entire dual-sequencing/row-locked-OCC/three-way-invariant design this plan is built around, for no architectural benefit.
- **MongoDB is the read side** — the CQRS query model (`order_summary`, `payment_summary`, `shipment_summary`) lives in a MongoDB `chronoscope_read` database. Projections are exactly the "denormalized, per-query-shape, fully rebuildable, no cross-document transactional requirement" workload MongoDB is built for, and the project demonstrates keeping two different database engines consistent across a crash using the same idempotency/ordered-commit vocabulary already established for Kafka and RabbitMQ (rule 10).

See `docs/architecture/database-ownership.md` for the full schema-by-schema, role-by-role breakdown.

## The 25 non-negotiable architecture rules

1. **MySQL is the sole authoritative business-state store.** Parameterized SQL only via `mysql2` (`?` placeholders), no ORM, no dynamic SQL identifiers except through a hardcoded allowlist. Schema via ordered, checksummed migrations applied under a MySQL named lock (`GET_LOCK('chronoscope:migrations', timeout)`, released in a `finally`), run only as `chronoscope_migrator`.
2. Domain code never contains SQL or Mongo driver calls; the API never contains either. Flow: `API → application service → domain (loads state, decides, computes newState+events) → repository interface → engine-specific repository (persists what domain already decided) → MySQL/MongoDB`. Neither database package ever invokes a domain reducer.
3. Events are immutable — enforced at two independent layers on MySQL: the `chronoscope_app` role gets `SELECT, INSERT` only on `events`/`system_events`, and a `BEFORE UPDATE`/`BEFORE DELETE` trigger (`SIGNAL SQLSTATE '45000'`, Phase 14) rejects mutation regardless of role. Domain events and system/operational events are physically separate tables; only domain events carry replay-determinism guarantees.
4. Every event carries `schema_version`; upcasters are mandatory before replaying historical payloads. `application_version`, `event_schema_version`, and `domain_logic_version` are tracked as three separate axes.
5. **Two sequence numbers with formally distinct semantics — never interchange their generation mechanism**: `aggregate_sequence` (scope: one `(timeline_id, aggregate_id)`; transactionally derived from the locked `aggregate_versions.current_sequence` row, **never** an `AUTO_INCREMENT` column; contiguous for committed events; used for OCC) and `timeline_position` (scope: one `timeline_id`; allocated from the `timeline_position_seq` AUTO_INCREMENT-table pattern; gaps expected; a logical ordering key, not causal order — the only causal relationship is `causation_id → event_id`). Both `UNIQUE KEY`s explicitly named for duplicate-key disambiguation.
6. **Event append locks only the `aggregate_versions` row — never a timeline-wide lock.** `timeline_position` is harvested via `INSERT INTO timeline_position_seq () VALUES ()` + `LAST_INSERT_ID()`, safe under `innodb_autoinc_lock_mode = 2` — MySQL 8.4 already defaults to this, but CHRONOSCOPE **pins it explicitly** in server config (`infrastructure/docker/mysql/my.cnf`) rather than relying on the default, so the concurrency contract this whole design depends on can't silently regress. Independent aggregates append fully concurrently; only same-aggregate commands contend, which is the intended OCC conflict. `timelines.head_position` is a best-effort cache (`GREATEST`), authoritative value `COALESCE(MAX(events.timeline_position), 0)`. A duplicate-`event_id` key violation is distinguished from a genuine `expectedSequence` mismatch by which named `UNIQUE KEY` the `ER_DUP_ENTRY` error names. **Fork position validation**: `fork_position = 0` valid; `0 <= fork_position <= COALESCE(MAX(parent.events.timeline_position), 0)`, checked transactionally.
7. **A command targets exactly one aggregate.** 0, 1, or many events, all belonging to that aggregate — never a multi-aggregate command. Cross-aggregate workflows are separate, orchestrator-coordinated commands.
8. **Three independent idempotency boundaries at the write side**: command dedup (`command_id`), event inbox (`event_id + consumer_name`, MySQL `chronoscope_ops`), job idempotency (`job_type + idempotency_key`, `NOT NULL`, carrying `result_reference`). Jobs have `RETRY_PENDING` distinct from terminal `FAILED`. Guarantee everywhere: **at-most-once application of the persistent effect despite at-least-once delivery.**
9. **`aggregate_state`** (MySQL) is an independent, incrementally-maintained materialization of current state, updated in the same MySQL transaction as the event append — this makes the write-side hash-parity proof non-circular: live hash = `aggregate_state.state_hash`, compared against replay hash computed after the fact. **Three-way invariant**: `aggregate_versions.current_sequence == aggregate_state.aggregate_sequence == MAX(events.aggregate_sequence)`. State/event hashing excludes event/transport identity.
10. **The event pipeline is at-least-once, a three-step cross-engine chain on the read side.** Write side: transactional MySQL outbox → Kafka (keyed `timelineId:aggregateId`) → SQL commit always precedes Kafka offset commit. Read side: (a) idempotent, sequence-guarded MongoDB upsert keyed by `` `${timelineId}:${aggregateId}` `` (`w:1,j:true`); **then** (b) MySQL inbox+checkpoint commit; **then** (c) Kafka offset commit — never reordered. `projection_checkpoints.kafka_offset` is the **last-processed** offset (not Kafka's own next-offset convention): `committedKafkaOffset == kafka_offset + 1` in the steady state. Exactly one projection operation in flight per Kafka partition per projection. Mongo data lost _after_ (b)/(c) is outside Kafka redelivery — recovery is `chronoscope rebuild-projection`, not a retry.
11. Replay is deterministic: canonical JSON, canonical numeric representation, canonical `CHAR(64)` hashes. Every event carries `event_hash`. Two distinct read-side hash concepts, never confused with `aggregate_state.state_hash`: `sourceStateHash`/`sourceAggregateSequence` (authoritative state at exactly that sequence, verified via a single shared `AuthoritativeStateResolver` when lagging) and `projectionHash` (the document's own content). Collection-level `source_manifest_hash`/`projection_collection_hash` in `projection_metadata` are frozen proofs of the last successful rebuild, never live-recomputed.
12. Replay has two structurally distinct modes: `LIVE_REPLAY` (read-only against MySQL) and `COUNTERFACTUAL_REPLAY` (branch-local MySQL events, driven by persisted `scenario_inputs`). Neither writes to MongoDB directly.
13. **Branches never copy parent history**, resolved via `WITH RECURSIVE` over `parent_timeline_id`. `aggregate_sequence` is branch-local, never inherited. A branch aggregate initializes at `aggregate_sequence = 0` with `state = EffectiveHistory(parent, ≤fork_position)`; its first local event advances sequence to 1. MongoDB projection bootstrap for a branch must derive the same fork-base state from MySQL before folding in the branch-local event.
14. Snapshots exist at two scopes (per-aggregate, timeline-level `snapshot_sets`), metadata in MySQL, payload in MinIO. A `READY` `snapshot_set` is a consistent cut via `START TRANSACTION WITH CONSISTENT SNAPSHOT`.
15. One aggregate = one ordered event stream; compensation map specified, built only when needed. Amounts use `currency` + `amount_minor BIGINT`.
16. Commands have typed failure categories and retry classification. Command dedup stores the full outcome. First command against a new aggregate uses `expectedSequence=0`, race handled via `INSERT IGNORE`. `aggregate_type` immutable per `aggregate_id`.
17. Projection workers may only write their own MongoDB collection and, on MySQL, only `inbox`/`projection_checkpoints` — never `projection_metadata`/`projection_rebuild_cutoffs`. Enforced by a per-`(projection, partition)` MySQL advisory fence (bounded lock name), not a bare status check.
18. NATS carries durable desired-state (`worker_controls`, OCC-versioned) and durable one-shot commands (`control_commands`, idempotent, two-phase cancellation) — both in MySQL. NATS is transport only.
19. gRPC's one responsibility: synchronous API⇄replay-worker calls, returning `{executionId, stateHash, summary}`, never bulk results inline.
20. Redis: rate limiting / cache / heartbeat only, never correctness.
21. Chaos faults typed by layer; application-level in-process, infrastructure-level via a separate optional Chaos Agent.
22. Every experiment run reproducible from a manifest recording exact patch versions and image digests, not bare major versions.
23. Recovery covers eight independent paths, including MongoDB read-side recovery (drop the collection, rebuild from MySQL, hash-verify).
24. `chronoscope audit --quick` (live-tolerant) / `--deep` (quiesced, strict) — see `docs/architecture/invariant-enforcement.md` for the exact checks.
25. Docker Compose is the local orchestrator; see `docs/architecture/data-classification.md` for per-store durability/truth/rebuildability.
